# 探索地图

> 目的：让你在不读 38 个 domain 的前提下，知道"想改的东西在哪、改了会波及什么"。
> 所有 `domain/base` 的位置都是**只读**——在 lab 里先用变体包一层验证，结论出来再回主仓改。

## A. 壳与两条侧栏

| 项 | 位置 | 现状 |
|---|---|---|
| 壳层布局 | `domain/base/src/web/src/components/layouts/app-layout/app-layout.tsx` | 左侧导航常驻，内容区在右 |
| lab 的数据注入层 | `app/src/web.lab/src/components/layouts/app-layout/app-layout.tsx` | 从正式版抄来：查询 profile/workspace/权限，再喂给 base |
| 项目详情里的**第二条**侧栏 | `domain/accounting/src/web/src/features/cfp/project-detail/page.tsx:470` | `expandedWidth="14rem"`，与壳层侧栏**没有互斥机制** |
| 它的骨架屏 | `domain/accounting/.../project-detail-skeleton.tsx:36` | `hidden w-56 … lg:flex` |

**这就是 N07/N08/2.1 的共同根因**：1280 宽下两条侧栏吃掉约 430px，工具栏和图表被挤。

在 lab 里试：新建 `v2-layout.tsx` 变体，只改内容区宽度分配（或让两条侧栏互斥），`?v=v2` 对比。

**波及**：所有 `/project/*` 详情页；面包屑；1400 以下的所有列表页。

## B. 导航与信息架构

| 项 | 位置 | 现状 |
|---|---|---|
| 场景 → 分类 → 项 | `app/src/web.lab/src/components/layouts/app-layout/app-nav-config.ts`（523 行） | 三层嵌套，最长前缀匹配决定面包屑 |
| 渲染器 | `domain/base/src/web/src/components/layouts/app-layout/nav-config.tsx` | 只负责画，不负责过滤 |
| 面包屑 | `domain/base/src/web/src/components/layouts/app-layout/breadcrumbs.tsx` | 依赖 `sidebarState` 的 activeScene |
| 企业门禁 | `app-nav-config.ts` 里的 `filterManagementCategoryByOrganizationType` | 非企业客户组织隐藏整个「管理」分类 |

**N09 的成因**：动作入口（通知/工作台）指向的路由，在非企业组织下所属分类被隐藏 → 无 activeScene → 面包屑回退到默认场景。

在 lab 里试：改 `app-nav-config.ts` 的分类与可见性；或在变体里加"面包屑走路由元数据"的兜底。

**波及**：面包屑、通知跳转、工作台入口、`/admin` 链接。

## C. 断点与内容区宽度

| 项 | 位置 | 现状 |
|---|---|---|
| 响应式类 | 散落在 **330 个文件** 里（`sm:` / `lg:` / `xl:`） | 全部是**视口断点**，不是容器断点 |
| 全局样式 | `domain/base/src/web/src/styles/globals.css`、`custom.css` | 无 container query 基础设施 |

典型三处：`sm:flex-nowrap`（工具栏不换行）、`xl` 并排 + `minmax(280/320)`、`lg:grid-cols-3`（4 张卡必然 3+1）。

在 lab 里试：给内容区加 `container-type: inline-size`，把某个页面的 `lg:` 换成 `@lg:`，三档截图对比。

**波及**：一次改对所有页面生效，风险也在这里——先在 2~3 个页面验证再铺开。

## D. 列表（最高杠杆）

| 项 | 位置 | 现状 |
|---|---|---|
| `DataView` / `useDataModel` / `createDataColumnBuilder` | **`@crew-ui/base`（外部 npm 包，v5.0.0）** | 不在本仓库里，改不了源码 |
| 调用点 | **79 个文件** | 项目列表、数据记录、核算列表、因子库、供应链、工时监督等 |
| 日期/数字格式化 | 各 domain 自己实现（53 处日期函数） | 三套精度、两种时区 |

关键结论：**列表默认值不是改一个组件，而是"外部依赖 + 79 个调用点"**。所以有两条路：

1. lab 里包一层 `LabDataView`（注入默认固定列/密度/选择语义），验证完给出"改哪几个 prop"的清单；
2. 结论回主仓后，评估是升级 `@crew-ui/base`、还是按页面显式传参。

**波及**：79 个列表页 + 所有导出/打印入口。

## E. 表单与弹窗

| 项 | 位置 | 现状 |
|---|---|---|
| 字段 | `domain/base/src/web/src/components/ui/field.tsx` | `FieldLabel` 不传 `htmlFor`，必填是裸 `*` |

**波及**：200 个弹窗；路由级 `useBlocker` 会影响所有页面切换。

## 成本速查

| 面 | 改动半径 | 需要动 base | 适合先做 |
|---|---|---|---|
| A 壳与侧栏 | 中大（全局布局） | 否，变体可包 | ✅ 最高优先 |
| B 导航/面包屑 | 中（导航 + 面包屑） | 否，app 层可改 | ✅ |
| C 断点 | 大（330 文件） | 否，可局部试点 | 先 2~3 页 |
| D 列表 | 大（外部包 + 79 页） | 否，包适配层 | 需要最多时间 |
| E 表单 | 大（200 弹窗） | 部分是（field.tsx） | 先 5 个 |
| F 文案 | 小 | 否 | 热身 |

## 一条经验

先在 **A + B** 上花时间：它们决定"内容区有多宽、当前在哪"，后面 C/D/E 的很多问题会自动变轻。反过来先调 C 的间距，会发现怎么调都差一点——因为根因在 A。
